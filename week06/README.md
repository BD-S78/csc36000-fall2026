## What is already running

`node.py` is the process: gRPC, peers, pause/drop/delay, a byte store. `client.py` talks to it. The process does not implement partitioning, copies, leader election, or 2PC — that is the plugin.

Files marked **Do not edit this file** (`node.py`, `client.py`, `util.py`, `modes.py`, `base.py`, the proto and generated stubs, `requirements.txt`) stay as they are. The file each student changes is the plugin they claimed.

The methods to fill in are already stubbed in **the one file that student claimed**. `base.py` has `PluginBase` (subclass that) and a short list of what a plugin can use on `node` (`node.store`, `node.log`, `node.leader`, …). A plugin sends messages with `node.rpc(peer_id, "Write", request)` (or `"Replicate"`, `"Elect"`, `"Prepare"`, …). That call honors the fault flags, so a paused node really blocks the RPC.

Until a method is filled in, the node still boots (keys on the first peer, a local Write, that peer as leader). That is so the group can start a cluster today. The claimed `Plugin` class is the protocol that makes the modes below actually happen. Membership is `node.nodes` — however many processes appear in `--peers` or `cluster.json`.

cd week06

### partitioning.py

**In the readings:** partitioning / sharding — *Think Distributed Systems* ch. 7; *Designing Data-Intensive Applications* ch. 7 (hash modulo, key range, consistent hashing).

**Modes:** at least three of `HASH_MOD`, `KEY_RANGE`, `SLOTS`, `DIRECTORY`, `ITEM`, including hash and slots.

Which node stores a key. `N` is `len(node.nodes)`. HASH_MOD remaps most keys when a member is added; SLOTS moves about `1/(N+1)`.

**HASH_MOD.** Send about two dozen distinct Writes through one node with `--partitioning HASH_MOD` (request routing that can forward). The owners are not all that node. Then `add-node` a new id. Most of those keys change owner.

**SLOTS.** Same Writes with `--partitioning SLOTS`. Then `add-node`. About `1/(N+1)` of the keys change owner — far fewer than HASH_MOD.

**KEY_RANGE.** Keys whose first bytes are neighbors (`aa…`, `ab…`) share an owner. A key at the high end of the byte space can sit alone on one node.

**DIRECTORY.** `pin` key `k` to an existing node. After `add-node`, `k` is still on that node. After `rebalance`, a Read of `k` on the pinned node has the bytes — they moved, they did not only change owner in Status.

**ITEM.** A `pin` does not succeed (`ok=false`). The owner still comes from the key itself, not a directory.

### replication.py

**In the readings:** state-based vs log-based replication — *Think Distributed Systems* §8.4.4.

**Modes:** `STATE`, `LOG`, `LOG_WITH_SNAPSHOT`.

Sending a log of operations and a snapshot to a node that is far behind is a catch-up strategy for log replication. That is not the same idea as hybrid write completion (`ACK_QUORUM`).

Pause a node that is not the owner. Write key `alpha` = `one` on another node with `--write-completion ACK_ONE`.

- **STATE.** Unpause. After catch-up, Read `alpha` on the paused node returns `one`. It received the bytes; it did not need a history of operations.
- **LOG.** Same pause. Two Writes (`alpha=one`, then `alpha=two`). Unpause. Read on the paused node returns `two` only after both ops were applied in order.
- **LOG_WITH_SNAPSHOT.** Pause a node across several Writes so it is far behind. Catch-up may send a snapshot. Read on that node still matches the others. A snapshot does not hide a Write that already returned ok.

### write_completion.py

**In the readings:** when a write is complete: synchronous, asynchronous, hybrid (quorum) — *Think Distributed Systems* §8.4.3; *Database Internals* ch. 11 (quorums, incomplete write).

**Modes:** `ACK_ALL`, `ACK_ONE`, `ACK_QUORUM`.

**Hybrid** in §8.4.3 means quorum write completion (`ACK_QUORUM`).

W is computed from the current membership `N = len(node.nodes)`: **ACK_ONE** waits for 1, **ACK_QUORUM** for `N//2 + 1`, **ACK_ALL** for `N`.

- **ACK_ALL.** Pause any one member. Write does not return ok (it waits or times out). After unpause, Read on the paused node has the value.
- **ACK_ONE.** Pause any one member. Write still returns ok. Read on the paused node may still be empty — an incomplete write. Unpause that node; a later Read on it (or `rebalance`) repairs the copy so the bytes are there.
- **ACK_QUORUM.** Pause fewer than a majority and Write still returns ok. Pause enough that fewer than `N//2 + 1` members can ack, and Write times out. A later Read that hits only a paused node may still be old until repair.

### leader_replication.py

**In the readings:** single-leader, multileader, leaderless — *Think Distributed Systems* §8.4.5.

**Modes:** `SINGLE_LEADER`, `LEADERLESS`, `MULTI_LEADER`.

- **SINGLE_LEADER.** Status names a leader. A Write on a follower goes to that leader (the plugin forwards it), or fails with `not leader`. Isolate the leader from the others; Writes on the side that is not the leader do not succeed.
- **LEADERLESS.** Split the cluster in two. Write `alpha=L` on one side and `alpha=R` on the other both return ok. The two stores can differ until conflicts are resolved.
- **MULTI_LEADER.** More than one node may accept Writes. After a split, both sides can accept; this node also copies the Write to the other leaders it can still reach.

### conflicts.py

**In the readings:** conflicts: operation-based CRDT, state-based CRDT, application reconciliation — *Think Distributed Systems* §9.3.3.

**Modes:** `OP_CRDT`, `STATE_CRDT`, `APP_RECONCILE`.

After a split, one side’s Read of key `k` is the bytes `a,b` and the other side’s Read of `k` is `b,c`. Heal the network, then `rebalance` (anti-entropy). A later Read of `k` on **each** side should be:

- **OP_CRDT.** `a,b,c` (the pieces of both values, sorted, no duplicates). Neither side’s add is dropped. Sequential Writes on one node are not enough — the merge has to survive a split.
- **STATE_CRDT.** The same `a,b,c`, from version metadata, not from replaying a list of operations.
- **APP_RECONCILE.** One of the two values, the last Write that arrived. The other can disappear. It is not `a,b,c`.

### processing_guarantees.py

**In the readings:** at-most-once, at-least-once, exactly-once *processing* — *Think Distributed Systems* ch. 4.

**Modes:** `AT_MOST_ONCE`, `AT_LEAST_ONCE`, `EXACTLY_ONCE`; resume by `LOG` or `SNAPSHOT`.

A run has two steps: Write `k1=v1`, then Write `k2=v2`.

- **AT_MOST_ONCE.** Pause a member and use `ACK_ALL` so the first Write times out. The run may skip that step. The applied list need not include `k1`.
- **AT_LEAST_ONCE.** Same timeout: the run stops `uncertain`. Unpause, `run-resume`. `k1` is present. A naive retry can apply the step twice unless the Write is the same bytes.
- **EXACTLY_ONCE.** Retry with an idempotency key `run_id:step`. The step’s effect happens once.
- Resume **LOG** continues from the next unapplied step (including an in-doubt step). Resume **SNAPSHOT** continues from the snapshot step; a step that was not in the snapshot is not invented. Keep the run record on the node so resume still works after that process was paused.

### request_routing.py

**In the readings:** request routing — *Designing Data-Intensive Applications* ch. 7.

**Modes:** `FORWARD`, `DIRECTORY_TIER`, `CLIENT_AWARE`.

A key is owned by some node other than the node that received the Write.

- **FORWARD.** The node that received the Write sends it on. Read on the owner has the value. Each forward increments `hop`; after 8 the Write fails with `hop limit` rather than looping.
- **DIRECTORY_TIER.** It looks up the owner, then sends. Same stored value. A stale lookup retries once rather than dropping the bytes.
- **CLIENT_AWARE.** Write on a non-owner returns `not owner`. That call does not store the value on the owner.

### leader_election.py

**In the readings:** leader election: Bully, ring, and majority/term (Raft-style) — the algorithms that pick the leader in §8.4.5.

**Modes:** `BULLY`, `RING`, `RAFT_STYLE`.

- **BULLY.** Stop the current leader. The highest remaining id becomes leader. Split the network: each side can have a leader (the highest id on that side).
- **RING.** The successor of the failed leader (the next id in the ring of current members) takes over when it is reachable.
- **RAFT_STYLE.** After a split, a side smaller than majority (`N//2 + 1` of current membership) does not elect. Writes on that side stop. The majority side may elect.

### session_models.py

**In the readings:** session models (read-own-writes, monotonic reads) — *Database Internals* ch. 11.

**Modes:** `READ_OWN_WRITES`, `MONOTONIC_READS`, `NO_SESSION`.

Write `alpha=one` with `--session-id s1` on one node. Then Read `alpha` with the same session id on **another** node.

- **READ_OWN_WRITES.** That Read returns `one` even if the second node is stale (it waits or pulls). Sequence numbers, not “the last bytes I happened to store on this process.”
- **MONOTONIC_READS.** Two Reads in `s1`: the second is not an older value than the first (a lower sequence is refused or redirected).
- **NO_SESSION.** Read may return old bytes or miss; there is no extra rule.

### atomic_commit.py

**In the readings:** atomic commit and sagas — *Think Distributed Systems* ch. 6 (two-phase commit); saga compensation (week 2 additional reading).

**Modes:** `TWO_PC`, `SAGA`, `SINGLE_KEY_ONLY` on two keys.

Keys `a` and `b`.

- **TWO_PC.** A txn that Writes `a=A` and `b=B` makes both visible, or neither. Prepare is sent to the **owner of each key**. If that participant is paused, the txn does not commit (it blocks or fails) and a later Read never sees only one of the two keys committed.
- **SAGA.** Write `a`, then Write `b`. If `b` fails, `a` is restored to its previous bytes (compensation). There can be a window where only `a` has changed.
- **SINGLE_KEY_ONLY.** A two-key txn returns `two-key refused`. An ordinary single-key Write still works.
